**Решение**

[Контекст](./context.drawio)

[Контейнеры](./container.drawio)

При выборе технологического стека был использован принцип применения решений, уже интегрированных в существующую инфраструктуру организации. Для повышения производительности системы был внедрён механизм кэширования на базе Redis. Обмен сообщениями между компонентами системы осуществлялся посредством Kafka, что обеспечило высокую перспективность и адаптивность к будущим требованиям развития системы. Поскольку банковская АБС не поддерживала непосредственное взаимодействие с Kafka, был запланирован разработанный адаптер на основе Debezium. С учётом ограничений масштабируемости базы данных АБС рекомендовалось предусмотреть дополнительные ресурсы для вертикального масштабирования и возможную миграцию АБС на альтернативную базу данных.

Интеграция интернет-банка с Kafka также потребовала разработки адаптера. Для этой цели может быть использована стандартная библиотека Confluent.Kafka, обеспечивающая интеграцию Kafka в .Net-приложения. Взаимодействие между сервисами системы было организовано через Kafka, что гарантировало отказоустойчивость, масштабируемость и асинхронный характер работы.

Для повышения надёжности системы был внедрён резервный центр обработки данных (ЦОД) в режиме горячего резерва. Резервное копирование данных осуществлялось с использованием технологии Stretch Cluster, обеспечивающей синхронную репликацию данных на резервный ЦОД. Взаимодействие пользователей с интернет-банком и веб-сайтом банка осуществлялось по протоколу HTTPS. Все конфиденциальные данные шифровались при передаче между сервисами.

**Альтернативы**
Также возможно использование RabbitMQ как альтернативы. Это позволило бы избежать создания адаптеров для взаимодействия. Для горячего резервирования подходят такие методы, как MirrorMaker или Cluster Linking. Резервный кластер при этом может отставать.

**Недостатки, ограничения, риски**

Внедрение горячего резервирования вызывает сложности. Компания пока не имеет опыта работы с Kafka. Кроме того, этот метод резервирования может вызвать задержки в работе ЦОДов, особенно если они находятся далеко друг от друга.

Монолитная АБС — еще одно слабое место. Ее база данных не поддерживает горизонтальное масштабирование. Возможное решение — переход на другую базу данных и рефакторинг АБС с переходом к микросервисной архитектуре.
